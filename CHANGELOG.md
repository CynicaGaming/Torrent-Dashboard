## v0.5.165 — Restore Jellyfin 12 connections

Jellyfin 12 disabled the legacy X-Emby-Token authentication header by default, so the Jellyfin integration received HTTP 401. Torrent Dashboard now authenticates with the standard Authorization header, which Jellyfin has accepted since 10.8.

### What's changed

- Jellyfin status, scheduled tasks, and library refresh work again with Jellyfin 12.x servers.
- Existing Jellyfin API keys keep working; no settings changes are required.

### Fixes

- Jellyfin requests send Authorization: MediaBrowser Client=..., Device=..., DeviceId=..., Version=..., Token=... instead of the removed X-Emby-Token header.
- Hardening tests close their SQLite connections so the Windows validation jobs can delete temporary databases.

### Technical notes

- All Jellyfin calls share one request helper, so the header change covers status, health checks, scheduled tasks, library refresh, and the local recovery tool.
- Header values are quoted and escaped; the Authorization form is supported from Jellyfin 10.8 onward, so older servers keep working.

### Validation

- Jellyfin tests assert the MediaBrowser Authorization header and that the legacy X-Emby-Token header is no longer sent.
- Runs the standard Ubuntu/Windows Python 3.13/3.14 matrix, source updater build, and Windows executable smoke tests.

### Known issues

- Backup encryption remains opt-in; unencrypted portable backups can contain saved client and integration credentials and should be stored securely.
- Windows executables are not code-signed yet.
- qBittorrent and integration API keys are stored in plain text in config.json.

## v0.5.164 — Harden live status, HTTPS, and history writes

Fixes reliability, performance, and information-disclosure issues found in a code review: a stalled HTTPS client can no longer freeze the dashboard, the status collector can no longer die permanently, and history writes and qBittorrent polling load are greatly reduced.

### What's changed

- One stalled HTTPS connection no longer blocks every other browser; the TLS handshake now runs on the per-connection thread and TLS 1.2 is the minimum.
- Per-torrent history rows are written once per sample interval instead of every second, and retention cleanup runs every 10 minutes instead of every second.
- Completion notifications are delivered from a background queue so slow webhooks no longer stall live status.
- The dashboard no longer overlaps status polls, discards stale responses after switching servers, and polls every 5 seconds while the tab is hidden.

### Fixes

- The status collector logs and survives unexpected errors (for example a malformed history_sample_seconds) instead of stopping until restart.
- Failed GET requests return a JSON 400/500 response instead of dropping the connection.
- Single-argument log_error calls such as request timeouts no longer raise IndexError.
- An HTTP error on the qBittorrent re-login retry is reported with the normal error message instead of escaping as a raw HTTPError.
- Dashboard and notification settings are type- and range-checked; enabling HTTPS requires both a certificate and key path.

### Technical notes

- qBittorrent app/WebAPI versions are cached for 5 minutes and preferences for 30 seconds; saving client settings clears the cache.
- Sonarr/Radarr/Lidarr queue lookups used by torrent details are cached for 30 seconds per integration.
- After setup, /api/setup/status returns only completion state and /api/setup/network-interfaces returns 403; /health exposes process ID and paths only to loopback clients.
- Logins for unknown usernames run one PBKDF2 verification so response timing does not reveal valid usernames.
- Expired sessions and idle rate-limit entries are swept periodically.

### Validation

- Adds 17 regression tests covering history write throttling, collector resilience, notification dispatch, client caching, settings validation, endpoint disclosure, and login timing.
- Runs the standard Ubuntu/Windows Python 3.13/3.14 matrix, source updater build, and Windows executable smoke tests.

### Known issues

- Backup encryption remains opt-in; unencrypted portable backups can contain saved client and integration credentials and should be stored securely.
- Windows executables are not code-signed yet.
- qBittorrent and integration API keys are stored in plain text in config.json.
